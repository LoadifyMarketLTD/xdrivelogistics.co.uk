# Legacy onboarding legal resume repair - 2026-10-20

## Incident and scope

The onboarding reminder links lead to `/onboarding/resume`. Previously its init API rejected outdated/incomplete signup legal metadata before loading the existing application. A September applicant could authenticate but could not reach the current agreement form. Production read-only inspection found four active commercial applications with potentially affected legacy metadata. This is not a Stripe error.

## Repair

- Existing canonical applications can resume read-only despite stale/missing signup legal metadata or missing historical signer metadata. New registrations retain their existing legal validation. Saved account type, application ownership, ambiguity and Company Driver invitation guards remain authoritative.
- Normal resume now explicitly requests `resumeOnly`; old clients/callbacks with stale metadata are also supported. Resume does not rewrite progress, payload, signatures, status, tokens or invitations, and does not enqueue another email. Blocked profiles are not converted into pending profiles.
- Current agreements remain inside the existing account-specific onboarding form. Language choice, reading/selection, confirmations and typing the signer name remain deliberate actions. No acceptance is generated by resuming.
- Explicit material reacceptance is now bound to the canonical onboarding application, just like initial remediation. Otherwise the submission gate could not find the new signature. Historical acceptance records are never updated/deleted.
- Submission still requires signed evidence; it also uses the existing material-change evaluator to require current versions, language and document snapshots. An otherwise current historical signature is not retrospectively invalidated solely for later acknowledgement metadata.
- Resume and the shared agreement form use the synchronized auth token, with a bounded session lookup fallback. Server-side authentication remains mandatory. Resume/legal responses are private and non-cacheable.
- No Stripe, insurance, compliance approval, commercial-access policy or customer data was changed. No database migration is required.

## Validation

- 160 unit/contract tests passed across 15 files, including 36 legacy-resume/reacceptance cases and eight current-evidence checks. Tests include unchanged saved applications, new-signup rejection, valid new signup, invitation isolation, blocked profiles, explicit consent, old-history preservation and binding the new acceptance to the correct application.
- Ten local browser/API checks passed. Eight UI checks use explicitly intercepted legacy data for the four commercial account types at 390px and 1440px; no signing is submitted. One authenticated read-only init test uses the existing authorised E2E account. One check verifies unauthenticated denial. These are not real customer signings or completed customer onboardings.
- Fixture tests block service workers so worker-owned requests cannot bypass network interception and display unrelated real test-account data. The website service worker was not changed.
- Local webpack compilation succeeded; the Windows production build worker later exited natively with code 3221226505 during static generation. Do not label that local full build PASS. Netlify's mandatory production build/release gate must pass before publication can be claimed.
- Production publication and the same browser/read-only regression must be verified separately.

## Client continuity

The existing reminder link is retained. Applicants reload Resume onboarding, review/sign the current package when required, and continue their saved application. Previously current signatures need not be accepted again merely because old signup metadata remains old. Missing documents, Stripe setup or genuine compliance checks remain separate requirements.

The reported applicant's pre-repair baseline remained in_progress with submitted_at null and one old legal acceptance. Only read-only diagnostic queries were run against that applicant. Do not claim their new acceptance or submission is completed until it actually occurs.
